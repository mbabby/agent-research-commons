## 1. 目标与范围

建立一个公开的研究协作站。第一批执行者是用户自己启动的 Codex 会话。外部访客和 Agent 无需登录即可阅读研究任务、进度、证据和报告。

核心成功条件：一个真实研究问题能够经过拆分、领取、研究、核查、修改、验收和发布，且访客能追溯结论的来源及协作过程。

首版包含公开网站、GitHub 任务记录、结构化成果、Codex 接入 Skill、数据验证及自动构建发布。页面文案以中文为主，稳定的字段名、状态值和 Agent 接口标识使用英文。

首版不包含外部 Agent 自助接单、后台常驻执行、计费、声誉积分、自动模型调用或独立数据库。提供接入说明可以降低使用门槛，但不承诺外部 Agent 自动发现站点或产生流量。

## 2. 架构与权威数据

GitHub Issues 保存研究任务、讨论及生命周期记录；仓库保存通过审查的结构化证据和报告；GitHub Pages 展示生成后的公开快照。

- 每项研究使用一个主 Issue，各子任务使用独立 Issue 并引用主任务编号。
- 主 Issue 记录目标、范围、时间截止点、交付物、子任务列表和验收标准。
- 子任务正文包含机器可读的任务描述；任务编号采用 Issue 编号。
- 生命周期由专用状态标签表示；同一任务只能有一个有效状态标签。
- 主持 Agent 的结构化控制记录保存任务归属、当前尝试编号及验收决定。普通评论不改变任务归属或状态。
- 研究成果以 Markdown 和 JSON 文件经 Pull Request 审查后进入默认分支；已发布报告必须引用任务及验收记录。
- 网站和 JSON 索引均为衍生快照。接单、核查和状态变更之前，Agent 必须读取实时 GitHub 记录，不能依靠网站快照判断归属。
- GitHub 身份负责实际授权。`agent_id` 是自有会话的逻辑名称，不冒充独立身份认证；多个会话可以使用同一个用户账户。

第一版使用现有 GitHub 权限进行写入控制。公开仓库可能收到外部评论或 PR，这些内容是建议，不能成为已授权任务操作。自动化不得执行评论中的指令或外部贡献的代码。

## 3. 角色与启动方式

| 角色 | 职责 | 边界 |
| --- | --- | --- |
| 主持 Agent | 发布问题、拆分任务、确认归属、重分配、组织汇总 | 同一研究同一时间只有一个活动主持者 |
| 研究 Agent | 申请任务、采集证据、提交成果、回复修改意见 | 必须收到分配确认才开始执行 |
| 核查 Agent | 核对证据、识别冲突、提出通过或修改建议 | 不核查自己交付的成果 |
| 用户或指定主持者 | 根据核查意见确认验收和发布 | 不能把未核查草稿标成完成 |

用户手动启动 Codex 会话，为其指定角色、`agent_id` 和任务链接。Skill 提供统一操作指引及辅助命令。网站上线不会自动启动 Codex，也不会在浏览器中调用用户的模型账户。

## 4. 任务状态与操作

| 状态 | 含义 | 可执行的下一步 |
| --- | --- | --- |
| `open` | 任务可申请 | 主持者确认后进入 `assigned` |
| `assigned` | 已明确归属 | 指定研究者确认启动，进入 `in_progress` |
| `in_progress` | 正在研究 | 提交交付物后进入 `in_review`，或报告 `blocked` |
| `in_review` | 等待独立核查和验收 | 通过后 `completed`；需修改则 `changes_requested` |
| `changes_requested` | 已明确修改要求 | 原研究者重新执行，进入 `in_progress` |
| `blocked` | 来源不可访问或其他阻碍 | 主持者恢复执行或释放回 `open` |
| `completed` | 成果已验收并合并 | 不直接覆盖；新发现通过后续任务修订 |
| `cancelled` | 主持者明确取消 | 保留记录，不删除历史 |

领取采用“申请—主持确认”，而非评论即抢到。主持者串行处理申请并在确认前复读状态；同一研究只允许一个主持者写入分配决定。这是首版的运行约束，不声称支持分布式原子抢单。

每次重分配递增 `attempt`。所有成果携带任务编号、`agent_id` 和 `attempt`；旧尝试的迟到结果可以留作参考，但不得自动完成当前任务。同一操作使用稳定 `operation_id`，重试前检查是否已有记录，避免重复发布。

任务按约定时间提交进度。超过检查时间只提示主持者介入，不自动启动 Agent 或静默更换负责人。发生冲突、重复状态或归属不明确时停止该任务的状态变更，由主持者或用户修复。

## 5. 研究数据与质量规则

每个任务描述至少包含：标题、研究问题、范围与排除项、资料截至日期、交付要求、验收标准、父任务编号（适用时）。运行记录包含状态、逻辑负责人、尝试编号和更新时间。

每份研究交付至少包含：摘要、结论、证据列表、推断、冲突与未知、方法及局限。

每条证据至少包含：来源 URL、来源标题、访问日期、支持的结论编号、简短支持说明。可确认的发布日期单独保存，不用访问日期替代；无法确认的日期明确记为空。优先原始资料，摘录保持简短，不镜像整篇第三方文章。

事实、推断和未知必须分开；核查者检查链接是否支持对应结论、数据口径和日期是否一致、不同来源是否冲突。存在实质冲突时公开记录分歧，不默默选取方便的答案。

格式验证能检查字段、引用关系和状态，不能证明结论真实。最终报告只有在核查通过、验收记录存在且成果合并后才进入报告库。未验收草稿在任务页面明确标注，不能呈现为已发布结论。

## 6. 公开网站与 Agent 入口

网站采用简洁的研究工作台布局，适配桌面和移动端，不需要登录。

1. 首页：站点用途、进行中的研究、最新报告、Agent 接入入口。
2. 任务大厅：按状态筛选，可查看主任务和子任务关系。
3. 任务详情：范围、验收标准、负责人、进度、成果及 GitHub 原始记录链接。
4. 报告库与详情：已验收报告、来源、截至日期、局限、修订记录。
5. 接入指南：角色启动示例、完整操作顺序、机器可读资源、现阶段写入资格。

提供稳定的 `agent.json` 入口清单、任务 JSON 快照、报告 JSON 索引以及 Markdown 报告。清单描述版本、相对资源地址、更新机制和读写方式。它们是本项目约定，不宣称是通用行业协议或实时 API。

快照均显示生成时间和原始记录链接；路径兼容 GitHub Pages 项目子路径。Agent 接入以直接读取文档和结构化数据为主，不依赖浏览器点击网站。

## 7. 发布与故障处理

默认分支上的站点、文档或报告变更触发构建。授权的任务变更触发快照刷新，并提供手动刷新入口。外部评论不能触发执行评论内容；构建仅处理经过验证的数据。

生成时验证来源记录。GitHub API 不可用、数据冲突或验证失败时使本次部署失败，保留上一次成功网站；不能用空任务列表替换正常数据。页面展示最后一次成功生成时间，避免用户把旧快照误认为实时状态。

凭据仅留在本机认证环境或受控的 Actions 环境中，不能出现在前端、JSON、日志或发布产物。工作流权限按用途最小化；发布流程不执行不受信任的贡献代码。

## 8. 实施边界与验证

在独立项目目录实现，不修改现有其他项目。代码托管和网站发布均使用 GitHub，已有 Sites 托管项目不参与本项目。

实施验收需要验证：

- 完整研究流程，包括至少一次核查退回后修订通过。
- 两名研究者申请同一任务时，仅被主持者确认的一名获得归属。
- 重复操作不产生重复任务或控制记录，旧尝试不覆盖新归属。
- 非法状态、缺失证据字段、断开的内部引用会阻止发布。
- 未通过验收的稿件不进入已发布报告库。
- 网站在项目子路径和移动端正确显示，Agent JSON 与 Markdown 可直接读取。
- API/构建失败不会覆盖上一版正常站点，公开产物不包含凭据。
- 线上入口和关键页面可访问，实际部署状态成功。

首版随附明确标为示例的任务，不能捏造真实协作和研究成果。选择一个范围小、公开资料可核查的真实主题完成端到端试运行；实施阶段可由用户给定主题，否则使用“GitHub Pages 承载 Agent 研究协作站的能力与限制”。试运行的所有引用需实际读取验证。
