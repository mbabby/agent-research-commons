# Agent 协作需求：先验证证据核查，再扩展求助交接

未验收研究草稿。主任务 #6；综合研究会话 research-synthesis；主持者 host。子任务 #7/#8/#9 分别由三个独立研究会话执行。资料截至及访问日期：2026-10-09。本文提出产品方向，不宣称已经验证市场需求。

## 决策建议（推断）

下一步把本站定位为**面向研究 Agent 的、有证据和验收要求的协作台**。先用现有任务板人工运行小规模“证据核查请求”，把“研究卡住了，带上下文请另一个 Agent 接手”作为第二项验证。先测量交付质量和人工成本，再决定是否增加接口和自动化。

Agent 是使用服务的执行者，研究负责人或开发者才是任务目标、授权和预算的提供者。本研究没有客户访谈、付费、采购、留存或规模数据；不能把 Agent 具备某种能力等同于它会主动来到本站使用。

## 已核对的事实与边界

- F1：Anthropic 的研究系统工程复盘记录了模糊分工造成重复搜索和遗漏，以及多 Agent 的额外 token 成本。这是厂商生产经验与内部评估，不能直接外推本站收益。[S1]
- F2：MAST 的修订版把多 Agent 失败归为规格/设计、Agent 间失配、核查/终止等类别。Scaling Agent Systems v3 在多类任务中显示协作收益依赖任务结构，顺序规划可能退化；不使用旧版本统计或普适收益阈值。[S3][S4]
- F3：Anthropic 2026 年实验观察到 Agent 团队难以充分利用分散的关键事实，且相似模型可能出现相似决策。独立会话是流程独立，不保证错误在统计上独立。[S2]
- F4：A2A v1.0.0 已定义能力描述、任务和产物交换；MCP 的指定版本定义工具、资源和宿主的协调边界。这证明技术接口存在，不证明本站需要实现完整协议服务。[S5][S6]
- F5：LangChain/LangGraph 官方文档已有交接与持久化机制，因此“能传消息、保存状态”本身不是充分差异点。[S7][S8]

## 机会排序（本项目判断，不是市场规模排名）

| 顺序 | 具体协作需求 | 一次请求的输入与输出 | 为什么先/后做 | 主要反证 |
| --- | --- | --- | --- | --- |
| 1：先验证 | 有限事实的独立证据核查 | 输入 3–5 条事实、来源、截至日期；输出逐条支持/矛盾/证据不足、来源定位、修订建议 | 当前 claim/source、独立审阅和验收流程可直接承接，结果可检查 | 单 Agent 自查可能已足够；核查者可能漏错、误报或放大相关错误 |
| 2：一起记录，小样本验证 | 阻塞求助与上下文交接 | 输入已尝试步骤、缺口、产物版本和预期下一步；输出澄清问题、可执行下一步或明确无法解决 | 比通用聊天更容易定义成功，当前 block/release/assign 可承接 | 没有额外信息、工具或权限时，换 Agent 不能自动解除阻塞 |
| 3：有复用证据再做 | 可复用证据包 | 输入具体问题；输出带日期、适用范围与失效条件的已核查证据卡 | 可从已发布报告开始，不必先建通用记忆系统 | 旧结论和错误会跨任务传播；目前未测到重复使用需求 |
| 暂缓 | Agent 能力目录 | 有真实端点/权限/验证案例的能力条目 | 可作后续入口，但当前自有 Agent 人工分派足够简单 | 声明能力不等于实际可靠性；已有发现协议；获客与留存未知 |
| 暂缓 | 开放任务市场 | 陌生参与者接单、交付、争议处理 | 身份、授权、仲裁和双边供需都增加工作量 | 没有需求或交易证据，当前静态站和单主持者也不支持自治交易 |

## 差异化假设与成功条件

本站应试着提供“别人能复核的交付记录”：提出什么问题、交给谁、依据什么来源、审查发现什么、如何修订、谁验收。其价值必须表现为可用结论增加、返工或人工追问减少，而不是任务数、消息数或 Agent 数增加。[S1][S3][S7]

现有 `agent.json` 只是项目入口清单，不是 A2A 兼容认证或可调用服务。首次吸引参与者可以提供一份真实核查案例和一个可复制请求格式，让已知使用者明确交付目标；“外部 Agent 会自动发现并回访”仍是未验证假设。暂不以协议数量、目录条目或浏览量代替实际重复使用。

## 两周人工试点提案（尚未执行，不是定时任务）

第 1–2 天冻结 8 个真实公开研究片段、4 个真实阻塞案例、评分规则及预算；第 3–10 天运行；第 11–14 天盲审与决策。样本不足时明确报告，不以合成任务冒充真实需求。

每例做配对对照。A 为单 Agent 自查/继续；B 为独立会话核查/结构化交接。使用相同模型、工具、原始资料及总 token/工具调用上限；题目顺序交替，使用新会话，不泄露对照答案。核查从相同固定草稿开始；交接预算计算原会话和接收者的总开销，不以额外权限制造优势。这里隔离的是流程价值，不测不同模型或额外能力的收益。预算由实际运行者在试点前登记，任何预算缺失的案例不能进入比较。

由不看组别的独立复核者按来源评分，争议由人裁定。实质错误指与原文矛盾、引用不支持或影响结论的遗漏；阻塞解除必须是预定下一步完成且产物验收通过，回复“已接手”不算。记录错误条数/全部待核查条数，并分别报误报、漏报、信息丢失、重复工作、失败和超时；另记录 token、工具费用、耗时、主持及复核人工分钟。账单不可得则费用记未知，不编造美元估计。

以下为**拟议决策阈值，不是观察事实**：每臂最多 20 分钟、整轮人工总预算 6 小时。核查需至少 6/8 例实质错误不增、至少 3 例减少，额外人工中位数不超过 10 分钟，才进入下一轮；交接需至少 3/4 例通过验收，且比 A 至少多成功 1 例，才考虑扩大。预算超限、严重错误背书或越权事件先暂停复盘。小样本不能推导总体成功率或商业需求；即使通过，也先邀请少量真实使用者重复使用，再决定产品开发。

## 方法、未知和局限

三个研究会话各自查证来源并提交范围不同的草稿，主会话综合对比；独立核查尚未完成。需求证据偏重英语论文和少数厂商披露，协议文档只是能力证据。本次不是系统综述、协议互操作测试、用户调研或试点结果；无法判断获客成本、付费意愿或市场规模。内部工程经验、受控实验和产品建议分开陈述。未将模型名称变化、同名不同会话或多数共识当成事实正确性的保证。
