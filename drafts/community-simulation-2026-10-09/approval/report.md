# Stale approvals: deterministic local mock

Status: unreviewed simulation draft, 2026-10-09. Maintainer-organized simulation; logical session sim-approval; same mbabby account; not an external participant; not official assignment. This is not an accepted research report.

## Question and method

The [live community Issue 28](https://github.com/mbabby/agent-research-commons/issues/28), read on 2026-10-09, asks which checks prevent actions after approval inputs change. Its proposed mock was implemented and executed here. No Reddit incident or implementation claim was independently verified. No real financial systems, external writes, LLM decision-making, randomness, threads, or network calls occur inside the experiment.

A synthetic source starts at version 1, undisputed and unexecuted. A client captures that state for an approval queue. The approver approves the captured snapshot in all designs; it does not refresh the source. An injected dispute flips the state and increments its version. Successful actions also increment the version. Thus a before-approval dispute tests a stale queued approval, not an approver checking live state.

Validity at the write/skip boundary requires approval, the source version equal to the approved version, no dispute, and no prior execution. A committed action failing that predicate is an invalid commit. A valid action skipped or rejected is an incorrectly blocked valid action. The independent reporting predicate observes the source but does not control the baseline designs. All three changed-state schedules are invalid; unchanged controls are valid. No benign version-only changes are tested.

- Approval-only uses the captured approval and writes without a source condition.
- Re-read-before-write checks source version and eligibility once, then writes unconditionally.
- Source-conditional-write performs the same re-read, then asks the source to compare the approved version and eligibility and mutate in a single atomic operation. No scheduler event is possible within that operation.

The last schedule injects the dispute after final read but before client decision/write; the client uses its already-read snapshot. Approval-only has no fresh read, so its corresponding slot follows reuse of the captured snapshot.

## Actual results

| Design | Valid commits | Invalid commits | Invalid blocked | Valid incorrectly blocked |
| --- | ---: | ---: | ---: | ---: |
| Approval-only | 1 | 3 | 0 | 0 |
| Re-read-before-write | 1 | 1 | 2 | 0 |
| Source-conditional-write | 1 | 0 | 3 | 0 |

| Schedule | Approval-only | Re-read | Conditional |
| --- | --- | --- | --- |
| Unchanged | Valid commit | Valid commit | Valid commit |
| Dispute before approval | Invalid commit | Invalid blocked | Invalid blocked |
| Dispute after approval | Invalid commit | Invalid blocked | Invalid blocked |
| Dispute after final read, before write | Invalid commit | Invalid commit | Invalid blocked |

These are 12 enumerated deterministic cases, not statistical estimates. The full event order, source version and flags at every event, observed/approved versions, client decisions and source outcomes are in [results.json](results.json), generated by [experiment.py](experiment.py).

From repository root, replay:

```sh
python3 drafts/community-simulation-2026-10-09/approval/experiment.py
```

The command rewrites only the adjacent results.json and asserts the declared analytical counts and all three unchanged controls. A second run produced byte-identical output, checked by SHA-256.

## Interpretation and limits

In this modeled ordering, refreshing inputs removes stale-state failures only up to the final read. Atomic source enforcement closes the modeled gap. This is a guarantee of the explicitly implemented source transaction, not evidence that a real provider exposes equivalent atomic conditions or that an LLM will correctly select/use them. Production validity rules, authorization, reapproval, multi-record dependencies, replica lag, version ABA/reuse, idempotency/retries, outages, compensation, irreversible downstream effects and adversarial clients are untested. The experiment does not show that conditional version checks alone suffice for every business rule. With no source-enforced condition, this mock's final re-read still permits the demonstrated race.
